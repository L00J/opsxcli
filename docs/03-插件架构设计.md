# opsxcli 插件架构说明

## 📂 插件分类

### plugins/builtin/ - 内置基础命令

**定位**: 使用 Go 标准库实现的简单基础命令，无需依赖系统工具

**已实现命令**:
- **文件操作** (`fileops.go`): ls, cat, cp, mv, rm, mkdir, touch, grep
- **网络配置** (`network.go`): ifconfig, route, ip

**特点**:
- 完全独立，无需系统命令
- 代码简洁，易于维护
- 跨平台兼容
- 体积增加约 3-5MB

---

### 独立插件 - 网络诊断工具

虽然也属于基础工具，但因实现复杂度高，保持独立便于维护：

| 插件 | 功能 | 保持独立的原因 |
|------|------|----------------|
| **ping** | ICMP ping 测试 | 包含完整统计、TCP fallback、多种探测方式 |
| **traceroute** | 路由追踪 | ICMP/UDP/TCP 多种实现，复杂的 TTL 处理 |
| **telnet** | 终端仿真 | 完整的 telnet 协议实现 |
| **nc** | 网络瑞士军刀 | 功能丰富，支持 TCP/UDP、服务端/客户端 |
| **netstat** | 网络统计 | 包含 ss 命令，解析 /proc 文件系统 |

---

### 独立插件 - 高级网络工具

非基础工具，属于专业网络工具：

| 插件 | 功能 | 说明 |
|------|------|------|
| **nmap** | 端口扫描 | 专业网络扫描工具 |
| **wget** | 文件下载 | 完整的 HTTP 下载工具 |
| **request** | HTTP 请求 | RESTful API 测试工具 |

---

### 独立插件 - 数据库客户端

| **postgres** | PostgreSQL 客户端 | github.com/lib/pq |
| **redis** | Redis 客户端 | github.com/go-redis/redis |

### 独立插件 - SSH 工具

| 插件 | 功能 | 说明 |

| **ssh** | SSH 客户端 | 支持命令执行、端口转发、SFTP |

### 独立插件 - TUI 监控工具

## 🏗️ 架构原则

### 何时放入 plugins/builtin/

满足以下**所有**条件的命令适合放入 builtin：

1. ✅ 属于 POSIX 基础命令或网络基础配置
2. ✅ 使用 Go 标准库即可实现（或仅需 gopsutil 等轻量库）
3. ✅ 代码简洁，通常单文件 < 500 行
4. ✅ 功能明确，不需要复杂的协议处理

### 何时保持独立插件

满足以下**任一**条件的命令应该独立：

1. ❌ 实现复杂，代码量大（> 500 行）
2. ❌ 需要专门的协议处理（SSH, MySQL, Redis 等）
3. ❌ 需要外部依赖库
4. ❌ 是应用层工具，而非系统基础命令
5. ❌ opsxcli 的特色功能（TUI 监控等）

## 💡 优势

### 混合架构的好处

1. **清晰的模块边界**: builtin 管基础命令，其他复杂工具独立
2. **易于维护**: 每个复杂工具有自己的目录，修改不影响其他模块
3. **体积可控**: 只把简单命令放 builtin，避免膨胀
4. **扩展灵活**: 新增复杂工具不影响 builtin 结构

### 与纯 builtin 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| **全部放 builtin/** | 看起来整齐 | builtin 目录膨胀，难以维护 |
| **全部独立** | 灵活 | 基础命令过于分散 |
| **混合架构**（当前） | 平衡灵活性和组织性 | 需要明确分类标准 |

---

## 🎯 总结

**当前架构决策**:
- `plugins/builtin/` = 内置基础命令（Go标准库实现）
- 独立 `plugins/*` = 复杂工具、应用层服务、特色功能

这个架构在**代码组织、维护性、体积控制**之间取得了最佳平衡。
